# Local comparison — 2026-11-05

This is a local measurement on Neovim 0.12.6, not a universal engine ranking.
Four alternating rounds produced 1,000 successful samples per input case/engine:
32,000 measured input operations, with zero correctness failures. Each engine also
has 20 fresh module loads, four collection-scaling rounds and 1,000 lifecycle cycles.

The new engine loads faster and has an effective literal-trigger index. It does
not win all editing workloads: with isolated equivalent definitions, LuaSnip is
faster for the 100-field table and 100-mirror update. In the actual configuration,
the new Markdown table route is substantially faster, but that comparison includes
the existing compatibility layer, decorations, inherited definitions and retained
state. LuaSnip's repeated configured table case slows further within each round.
Those configured numbers should not be presented as fresh-session engine costs.

Selected P50 figures, **snippet-tools / LuaSnip**, milliseconds:

- Module require: 1.027 / 6.073.
- Isolated 10×10 dynamic table: 17.210 / 3.260.
- Isolated 100-mirror update: 24.148 / 13.326.
- Configured repeated 10×10 table: 38.837 / 685.035.

The next optimization targets for snippet-tools are large-node expansion and many
mirror updates. These measurements locate slow operations; they do not yet
attribute the time to specific internal functions or justify a language rewrite.

In the isolated lifecycle workload, retained Lua heap grows by about 224–229 KiB
on both engines after 1,000 measured cycles (undo/backend bookkeeping is retained).
The new engine ends with zero buffer extmarks; LuaSnip grows from 105 to 1,105.
That mark-count trend merits cleanup investigation, but does not establish a
general Lua memory leak. Both retain one buffer and no growing autocommand count.

Configured figure-update round medians vary from roughly 6 to 61 ms on both routes;
there is no stable winner for that operation in this run.

## Limits

- warm filesystem caches; fresh-process module load is not an OS-cold boot
- UI includes PTY/controller/transport overhead and forced redraw; not physical display latency
- configured track keeps both engines loaded and includes compatibility/decorations differences
- RSS includes Neovim/C allocations; Lua heap is full-GC retained memory
- core match uses pinned LuaSnip internal collection API and excludes UI/context extraction
- Definition sets are preloaded for the configured route, so lazy source availability is not mistaken for speed.
- Normalized-history isolated memory results do not predict the real configuration's history retention.
- A large relative ratio on a sub-millisecond operation can still be a small absolute difference.
- The machine remains a shared interactive environment; tails and small differences can vary between runs.

## Run provenance

This run was resumed with unchanged input-protocol hashes and source revisions. Completed input samples were retained.

The core harness changed on resume, so both engines' core samples were rerun. Previous completed core samples remain under discarded_core and are excluded from summaries.

The initial fixed-10-call core process exceeded its 180-second whole-process limit on luasnip. It was replaced by calibrated 1–10-call batches. This is a batch-runtime timeout, not a single-operation latency or input correctness failure.
